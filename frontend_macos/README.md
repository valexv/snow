# Snow for macOS (SwiftUI)

A native macOS frontend for Snow, written in SwiftUI. The emulator core is the same
Rust code used by the cross-platform egui frontend (`frontend_egui`), which is still
the frontend for every platform, macOS included.

## Layout

- `Snow.xcodeproj`: the app. Files added to `Snow/` are picked up automatically.
- `Snow/`: the SwiftUI app.
- `Snow/Generated/`: Swift bindings to the Rust core, generated by
  [UniFFI](https://mozilla.github.io/uniffi-rs). Don't edit them by hand.
- `snow_ffi/`: a Rust crate (a workspace member) exposing `snow_core` to Swift
  through UniFFI.
- `uniffi-bindgen/`: the UniFFI binding generator, pinned to the same UniFFI version
  as `snow_ffi`.
- `build_rust.sh`: builds `libsnow_ffi.a` and regenerates the bindings. Xcode runs
  it before compiling Swift.

## Building

Install Rust with [rustup](https://rustup.rs) and Xcode 26 or later, then open
`Snow.xcodeproj` and run, or:

```sh
xcodebuild -project frontend_macos/Snow.xcodeproj -scheme Snow -configuration Release build
```

The build script installs the Rust targets it needs through rustup and builds
whichever architectures Xcode is building, combining them with `lipo` for a
universal build. Rust's build output goes to `target/xcode`, apart from the egui
frontend's.

The Rust core is always built optimized, since an unoptimized emulator is too slow to
use. To debug the Rust side, set `SNOW_RUST_PROFILE=dev` in the scheme's build
environment.

`cargo build` at the workspace root still builds only the egui frontend.

## Using it

- **Machines** are listed in the sidebar. **File > New Macintosh…** (or **+** while
  the sidebar is open) sets one up from a ROM: the model is detected from it, and
  you pick the memory, the monitor where the model can drive more than one, and
  optionally a new blank hard disk (20 MB to 4 GB), which is created in the
  machine's folder at SCSI ID 0. The Macintosh II family also needs its display
  card ROM, which tells which card it has, and the SE/30 its video ROM.
  **File > Import Snow Workspace…** adds a workspace made with the egui frontend.
- **The inspector** (the toolbar's settings button, or ⌃⌘I) shows the selected
  machine's settings in a panel over the side of its screen, which keeps its size.
  Changes are saved as they're made. The exception is hardware changes to a machine
  that's running or suspended: its state only matches the hardware it has, so those
  wait for **Apply**, which starts the machine over.
  **Hard Disks** lists the machine's disks. Its **Add Disk** menu makes a blank one
  in the machine's folder (**New Disk…**, in the sizes the new machine sheet offers)
  or adds an existing image. **CD-ROM** lists its drives. A drive holds a disc image
  (`.iso`, `.toast`, `.cue`), or a folder whose files are made into a disc each time
  it's inserted (as the egui frontend's "Mount image from files"; subfolders and
  hidden files are left out). A drive can also be a Toolbox managed folder of disc
  images, which the Mac switches between with the BlueSCSI Toolbox. Adding or
  removing drives is a hardware change; changing the disc isn't, and a running
  machine gets the new disc at once. A disc the guest ejects is taken out of the
  settings too, so the drive shows as empty. The disc in each drive is kept in the
  workspace's `cdrom_discs` field, which only this app reads: the egui frontend
  only inserts discs into a running machine.
  **Network** adds an Ethernet controller (a DaynaPORT SCSI/Link, at SCSI ID 3 if
  it's free, where its drivers find it best) and picks its connection, as the egui
  frontend offers on macOS: not connected, NAT, or NAT with HTTPS stripping. Adding
  or removing the controller is a hardware change; the connection changes at once.
  The connection is kept in the egui frontend's `ethernet_link_type` field.
  **Printer** adds a LaserWriter IISC (at SCSI ID 4 if it's free, where its driver
  looks first). As in the egui frontend, each page it prints is saved to the
  Desktop as a PNG image, and a banner says so.
  Its **Video** tab sets how the screen is shown, and changes it as you go: scaling
  to fit the window (or the actual size), only by whole numbers, at the real size of
  the machine's screen (from both screens' pixels per inch), the scaling filter,
  and a CRT effect. The effect has no settings of its own: it looks like the
  machine's screen (its built-in display or its monitor), and changes with the
  monitor. The scaling filter and the effect's switch are kept in the same workspace
  fields as the egui frontend's (`scaling_algorithm`, `shader_enabled`); the egui
  frontend's own shader settings are left as they are.
- **Selecting another machine suspends the running one** and resumes the selected one
  where it left off. Quitting suspends the running machine too, and the app resumes
  it at the next launch. **Power Off** stops a machine without saving its state, so it
  starts fresh next time.
- **Mute** in the toolbar silences the running machine, and stays on for every
  machine until it's turned off. Machines always start with sound: the egui
  frontend's "disable audio" option, kept in the workspace, isn't used here.
- **Fast Forward** in the toolbar runs the machine as fast as it can, except while it
  plays sound. A machine fast-forwarding when it stops starts fast-forwarding again,
  fresh or resumed; it's kept as the workspace's "start in fast-forward mode".
- **Take Screenshot** in the toolbar saves the screen to the Desktop as a PNG image,
  named as the egui frontend names its screenshots.
- Floppy images can be inserted from the toolbar or the Drives menu, or dropped onto
  the screen. A dropped floppy image goes into the first empty floppy drive.
- The toolbar and the Drives menu show each CD-ROM drive, after the floppy drives.
  An empty drive takes a disc image or a folder made into a disc; a drive with a
  disc shows it, as only the guest ejects discs. A model that can have a CD-ROM drive
  shows one even without any, and inserting a disc adds it while the machine runs.
- A CD-ROM image (`.iso`, `.toast`, `.cue`) dropped onto the screen goes into an
  empty CD-ROM drive. A machine without a CD-ROM drive gets one, added while it
  runs. The disc and drive are saved in its settings. Dropping never replaces a disk
  already in a drive.
- While the screen has focus, every key goes to the guest, Command shortcuts
  included. The app's own shortcuts use Control-Command: ⌃⌘N new Macintosh,
  ⌃⌘I settings, ⌃⌘P pause, ⌃⌘R reset (or start/resume), ⌃⌘S export state,
  ⌃⌘Q power off.

## Where machines are kept

Each machine is a folder in `~/Library/Application Support/Snow/Machines/`, named
after the machine:

- `Machine.snoww`: a Snow workspace with the machine's settings. The egui frontend can
  open it too. This app only changes the settings it shows, and keeps the rest of the
  file (such as the egui frontend's window layout) as it is.
- `State.snows`: the state the machine was suspended in, if it is suspended.
- `PRAM.pram`: its PRAM, which the machine keeps between starts.
- `Hard Disk.img`: the hard disk, if one was created with the machine, and any
  made in the inspector.
- Copies of its ROM and display ROM, made when the machine is created or a ROM is
  changed in the inspector. ROMs it used before stay in the folder.

Other disk images stay where you chose them; the workspace refers to them.

A save state contains a copy of each hard disk. While a resumed machine runs, the core
works on those copies in a temporary directory. When the machine is suspended or
powered off, the copies are written back to the disk images, so the images always
have the latest contents, even if a saved state can't be restored later. If the app
is killed while a resumed machine runs, its disks and state stay as they were at the
last suspend.

## Exposing more of the core

Swift only sees what `snow_ffi/src/lib.rs` exports. Add a method to the
`#[uniffi::export] impl Machine` block, or a `#[uniffi::export]` function, and use
`#[derive(uniffi::Record)]` or `#[derive(uniffi::Enum)]` for the types it takes or
returns. The next build regenerates `Snow/Generated/`, and the new API is available in
Swift under camelCase names.

The bridge drives the emulator with the same `EmulatorCommand`/`EmulatorEvent`
channels as `frontend_egui/src/emulator.rs`, which is the reference for what the core
can do.

A few things to know:

- **Commit `Snow/Generated/`.** Xcode decides which Swift files to compile before
  running the build script, so the bindings must already exist when it does. After
  changing the Rust API, the build updates them; commit the result with the Rust
  change.
- **Upgrading UniFFI:** change the version in both `snow_ffi/Cargo.toml` and
  `uniffi-bindgen/Cargo.toml`. A mismatch makes the app stop at launch with a
  checksum error.
- **Actor isolation:** the target does not make everything `@MainActor` by default,
  because the generated bindings don't compile that way. Mark UI classes
  `@MainActor` yourself, as `EmulatorModel` is.

`cargo test -p snow_ffi` tests the workspace format against the egui frontend's
(fast-forwarding at start included), the suspend, resume and disk write-back cycle
using a blank ROM, the models' specs, display ROMs and video settings, discs made
from folders, and how dropped files are told apart.

The screen is drawn with Metal (`ScreenRenderer`). The CRT effect in
`Snow/Shaders.metal` is a Metal version of the egui frontend's CRT Lottes shader,
`frontend_egui/shaders/crt-lottes-fast.glsl`, so change it in both places. Its
settings for each screen are in `snow_ffi/src/video.rs`, which reads the parameters'
order and defaults from that GLSL file. The egui frontend renders it at the guest
display's size; here it renders at the window's resolution, so the settings are this
app's own. Building needs Xcode's Metal toolchain
(`xcodebuild -downloadComponent MetalToolchain`).

The audio output reuses `frontend_egui/src/audio_cpal.rs` through a `#[path]` module
rather than a copy, so changes there affect both frontends.
